## 1. 目标与前置输入

回答“用户实际经历了什么”，不提前解释隐藏 Agent、工具或后端实现。终点必须是证据能够证明的终点，而不是产品声明的理想终点。

最小输入：S0 来源、证据、冲突和覆盖记录；至少一个用户目标或入口；至少一个页面反馈或状态变化。只有历史总结、没有原始页面时，报告必须命名为“待验证版”，不能写“页面取证版”。

## 2. 操作方法

1. 找到最早可见的用户目标、输入和首次产品反馈。
2. 按“目标 → 动作 → 反馈 → 决定 → 状态/对象变化 → 下一步”建立事件链。
3. 每次确认、修改、返回或中断后，核对页面新增、修改、失效或保留了什么。
4. 对每次“完成”声明，分别检查运行状态、工作区、对象/资产库、历史和预览/消费结果。
5. 区分页面提供的分支入口与真正执行过的分支结果。
6. 先完成证据表，再绘制三类旅程路径；图不能产生表里没有的事实。

## 3. 固定内容结构

使用 [../assets/journey-report.html](../assets/journey-report.html)，严格保留以下八章及顺序，不额外插入“覆盖矩阵”“商业模型”或“停止边界”章节。相关内容分别并入查看范围、问题、机会或页脚。

### 1. 本次查看范围

首屏写清快照时间、来源数量、访问模式、允许/禁止动作、最早事件、证据终点和一句最重要结论。结论必须区分“存在阶段结果”和“最终可用结果”。

### 2. 无法访问或无法确认的证据

按“未确认项 / 当前证据 / 影响 / 最小补证动作”组织。未观察不等于不存在。

### 3. 用户旅程证据表

| 阶段 | 用户目标 | 用户动作 | 页面反馈 | 用户需要做的决定 | 页面/对象/资产变化 | 问题或阻力 | 证据 |
|---|---|---|---|---|---|---|---|

证据列至少包含：页面原文、控件名、行为主体、可见对象或错误、来源/截图编号、证据等级。每行保留 `data-evidence-id` 与 `data-source-id`。

### 4. 三泳道用户旅程图

必须分别绘制三块路径：

1. 正常主流程；
2. 用户修改/纠偏流程；
3. 失败与中断流程。

每块只保留“用户 / 产品界面 / 系统结果”三条泳道。判断节点使用菱形或 `.decision`，分支写明“满意/不满意”“成功/失败”“继续/中断”“余额充足/不足”等条件。未执行分支使用虚线和 `【尚未确认】`。每个事实节点显示证据芯片。

### 5. 用户情绪、想法与痛点

至少按关键阶段展示情绪分值或趋势、用户可能的想法、触发证据和具体痛点。情绪是分析者判断时必须标 `【合理推断】`，不得冒充用户原话。

痛点结构：触发事件、用户影响、证据、严重度、未确认部分。优先检查完成含义、依赖暴露、修改影响、版本恢复、成本时长、失败中断和最终就绪状态。

### 6. 三个最值得讨论的用户体验问题

固定输出三个，按影响排序。每个问题包含：页面事实、合理推断或未知、为什么影响用户、需要讨论的产品决定。

### 7. 如果做同类产品：产品机会点

按 P0/P1/P2 输出机会，说明对应痛点、建议机制和预期价值。所有机会属于建议，不能回写成当前产品事实。

### 8. 你的补充区

保留三个可编辑字段：用户情绪、最严重痛点、继续验证的证据。提供“保存补充”“导出补充 JSON”“清空本地补充”，只使用当前浏览器 `localStorage`，不得上传。

## 4. HTML 交互契约

- `data-report-profile="journey"`。
- 三类路径分别使用 `data-path-kind="normal|correction|failure"`。
- 情绪节点使用 `data-emotion-stage`，三个关键问题使用 `data-ux-issue`。
- 证据芯片可显示紧凑编号，规范编号写入 `data-evidence-id`。
- 页内导航顺序必须与八章一致；当前章节随滚动高亮。
- 三泳道允许容器内部横向滚动，整页不得横向溢出。
- 页脚写清停止边界和“没有修改目标产品”。

## 5. 质量门

- [ ] 八章完整且顺序一致，没有额外主章节。
- [ ] 起点、证据终点和最重要结论在首屏可见。
- [ ] 每次确认或修改后的真实变化已核对。
- [ ] 正常、修改、失败/中断三类路径齐全，未发生路径明确标灰。
- [ ] Agent 声明、运行结果、对象和最终可用性分别记录。
- [ ] 情绪、痛点和机会没有冒充页面事实。
- [ ] 三个体验问题和三个补充字段存在。
- [ ] 所有关键节点可回到证据表。
- [ ] HTML 交互和三档宽度检查通过。
