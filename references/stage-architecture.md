## 1. 目标与前置输入

把经过验证的用户行为、控制规则、工具、状态、数据和对象结果组合为可追溯架构。04 是完整交付中最后生成、最重要的核心总报告，必须显式整合 01 用户旅程、02 契约和 03 功能等价 Prompt 的结论与冲突。始终分开：As-Is 已确认、行为推导、To-Be 建议和未知。

最小输入：S0 台账、S1 用户旅程和证据终点；产品存在 Agent/自动化时加入 S2 契约；使用历史报告时抽样回查原始证据。

## 2. 五条端到端流

在同一真实任务上对齐：

1. 用户交互流；
2. 控制与工作流；
3. 工具与服务流；
4. 数据与状态流；
5. 对象与结果流。

流转表至少包含：步骤、触发者、处理者、读取、判断、工具/服务、结果对象、状态写回、确认门、下游、失败分支和证据。

## 3. 自适应架构内容

报告结构固定，架构层和组件必须按产品证据适配。候选层：用户与渠道、体验与工作台、产品与业务域、工作流与 Agent、工具/服务/集成、模型与决策、数据/状态/对象、知识/模板/政策、基础设施与治理。

删除没有证据也没有设计必要性的组件；对应固定章节仍保留，并明确写“本场景不适用”或“当前未知”，不得把 AI 视频产品的剧本、角色、分镜和九层技术栈强加给其他产品。

基础设施未公开时按“所需能力 / 候选类别 / 建议方案与理由 / 当前无法确认原因”描述，不把具体供应商写成事实。

## 4. 固定十八章

使用 [../assets/architecture-report.html](../assets/architecture-report.html)，HTML 源码和视觉顺序都必须如下，不依赖 JavaScript 重排：

1. 执行摘要；
2. 证据来源与证据缺口；
3. 核心功能域；
4. 端到端功能流转表；
5. 产品分层架构；
6. Agent、工具和全局上下文关系；
7. 全局上下文架构；
8. 知识与公共资产架构；
9. 模型接入与路由架构；
10. 底层架构选型表；
11. 数据实体表和 ER 图；
12. 端到端时序图；
13. 产品全景架构主图；
14. 当前架构 As-Is；
15. 建议架构 To-Be；
16. 关键架构风险；
17. 架构组件—证据追溯表；
18. 仍然无法确认的问题。

停止边界放入页脚，不增加第十九章。

## 5. 图表与 HTML 交互契约

- `data-report-profile="architecture"`。
- 证据等级统一使用 `confirmed|inference|recommendation|unknown`。
- 第 11、12、13 章分别提供 ER、时序和全景图的可阅读视图与可复制 Mermaid 源码；不适用时在对应章使用 `data-not-applicable-for` 写明理由。
- 时序图必须覆盖修改、失败或中断中的至少一种；全景图必须含动作语义箭头。
- 第 16 章风险按 P0/P1/P2 或影响×可能性排序，至少三项，参考级建议五项以上。
- 第 17 章提供四类证据筛选按钮；筛选只影响追溯表显示。
- 复杂图和表格只在自身容器内横向滚动。
- 页脚写停止边界和最重要的架构未知。

## 6. 质量门

- [ ] 十八章完整，源码与视觉顺序一致。
- [ ] 04 在 01—03 校验通过后生成，且能追溯其采用或拒绝的前序结论。
- [ ] 五条流在同一真实任务上对齐。
- [ ] 架构层和实体从产品证据出发，不是模板填空。
- [ ] As-Is、推导、To-Be 和未知可以独立辨认。
- [ ] 每个主图组件有证据、推导依据或设计理由。
- [ ] 上下文生产者、消费者、版本和失效关系清楚。
- [ ] 模型、知识、规则和用户私有数据边界清楚；不适用项已解释。
- [ ] 后端技术未被无证据写成事实。
- [ ] 状态冲突、失败、中断、重复执行和真实完成均有处理。
- [ ] ER、时序和全景图可读、可复制或有明确不适用理由。
- [ ] 风险和组件追溯可筛选。
- [ ] 三档宽度检查通过。
