## 1. 启用条件与识别边界

页面出现具名 Agent/机器人、明确阶段主体、可唯一归属的自动化职能或公开任务交接时启用。普通产品没有这些证据时，改为描述用户角色、业务规则、服务和状态机。

必须分开：界面身份、具名 Agent、职能自动化、工具/服务、仅推测主体。统一助手名不自动等于主控；最终结果需要某能力也不能证明存在对应 Agent。不要预设数量。

对每个主体记录首次出现、触发者、接替对象、重复出现、用户修改后的重触发、结束状态和下游交接。只有交接消息、阶段切换、任务事件或下游实际消费才能确认交接。

## 2. 六类输入和可观察判断

每个主体逐类检查；没有证据也写未知：

1. 用户当前输入；
2. 用户长期信息；
3. 项目全局上下文；
4. 上游 Agent 输出；
5. 平台公共资产、知识和规则；
6. 工具或运行时结果。

只总结功能判断：解决什么问题、输入是否齐全、何时确认或自动继续、何时停止/回退/重试、如何选工具、怎样判定完成、是否真正验证结果。不得输出隐藏推理过程。

## 3. 固定报告结构

使用 [../assets/agent-contract-report.html](../assets/agent-contract-report.html)，严格保留以下九章：

1. 查看范围与证据缺口；
2. Agent 清单；
3. 每个 Agent 的 I/O 契约卡；
4. 工具总表；
5. 全局上下文字段表；
6. 数据生产者—消费者关系表；
7. Agent 输入—判断—工具—输出—交接流程图；
8. 事实、推断和未知事项清单；
9. 最值得继续验证的五个问题。

“未观察主体”和停止边界分别放入第 2 章和页脚，不增加主章节。

## 4. 固定十段 I/O 契约卡

每个实际主体使用一张可折叠卡，严格使用十段，不增加第十一、十二段：

1. **核心目标**；
2. **触发条件**：同时写首次出现、触发者、接替/重触发和下游开始门；
3. **输入信息**：逐项列六类来源、必填/可选/未知、用途和证据；
4. **可观察判断**；
5. **调用工具**：区分 planned、claimed、runtime_visible、result_visible、consumed；
6. **输出信息**：覆盖用户回复、页面组件、结构化字段、对象/资产、状态和下游任务；
7. **全局上下文读写**：字段/对象、读写、生产者、消费者、更新时机、版本/失效和证据；
8. **完成条件**：不能只依赖自然语言“完成”；
9. **异常与重试**：失败、中断、额度、安全、重复执行和状态写入；
10. **尚未确认的问题**。

下游交接写入第 2、6、7、8 段，不再单列一段。

## 5. HTML 交互契约

- `data-report-profile="agent-contract"`。
- Agent 清单使用摘要卡，契约使用 `<details data-contract-card>`。
- 每张契约卡含 `data-contract-section="1"` 到 `"10"`。
- 提供搜索输入、事实/推断/未知筛选、全部展开和全部收起。
- 筛选和搜索只改变显示，不修改内容或证据等级。
- 工具名不可见时使用 `<功能工具>` 并标“非官方工具名”。
- 数据流图同时提供可读视图和可复制源码。
- 页脚写停止边界：本轮没有进入完整 System Prompt。

## 6. 质量门

- [ ] 九章完整且顺序一致。
- [ ] 每个清单项有页面名称、阶段标签或唯一职能证据。
- [ ] 界面身份、主控、专业主体、工具和服务没有混为一谈。
- [ ] 每张契约卡恰好包含十段。
- [ ] 六类输入、多类输出和工具执行等级均已检查。
- [ ] 上游、下游、触发、重触发和完成有证据或明确标为推断。
- [ ] 全局上下文能回到生产者、消费者、版本和失效关系。
- [ ] 搜索、筛选和展开收起可用。
- [ ] 第九章恰好列出五个最值得验证的问题。
